# S4: human review, exact-revision approval and export

## Scope and migration

S4 adds reviewer discovery/assignment, comments, reasoned finding resolutions, explicit per-category human checks, submission, final decisions and JSON export of approved content with its evidence record. It preserves all S1–S3 endpoints and adds `workflow_version` and `approval_stale` to content responses. Migration `0004_workflow` creates comments, finding resolutions, manual checks and decisions. PostgreSQL UPDATE triggers protect these historical records; tenant-constrained foreign keys prevent attaching them to another workspace/revision. Retention may eventually delete content through the separately authorised deletion workflow; history is immutable under UPDATE, not exempt from erasure requirements.

## Frontend sequence

All routes are under `/api/v1` and retain the session/CSRF contract. Membership IDs, not user IDs, identify reviewers. `GET /reviewers` returns only reviewer memberships from the caller's workspace with their email labels.

1. **Assign before resolving.** A manager can `PUT /content/{id}/reviewer` with `reviewer_id`, `expected_item_version` and a rationale (at least 20 nonblank characters). A creator can also select an authorised reviewer as part of submission. If the reviewer needs to inspect blockers or missing checks before submission, use the manager assignment step first. The assigned reviewer can access that content before final submission.
2. **Read and discuss.** `GET/POST /revisions/{id}/comments` supports revision-specific comments and optional `finding_id`. The API rejects a finding from another revision. Comments are text, never trusted HTML; the frontend must render them as text. A comment does not change content or invalidate a pending browser decision. Discussion after approval is allowed but does not rewrite the frozen approval record.
3. **Resolve findings.** `POST /findings/{id}/resolutions` takes `expected_item_version`, `action`, `rationale` and optional `source_version_ids` from that exact run snapshot. Creators may `request_exception` or `request_dismissal`; only the assigned separate reviewer may `confirm`, `dismiss`, `grant_exception` or `reject_exception`. A request alone never clears a blocker. Unsupported/contradicted fact or claim findings cannot be dismissed into correctness; correct/reanalyse them or grant an explicit reasoned exception. Exceptions are displayed as exceptions, not proof of truth. A new revision/run does not inherit a previous exception.
4. **Inspect check completion.** `GET /revisions/{id}/review` returns the latest run ID, current workflow version, staleness, evidence, effective check coverage and decision history. `GET /runs/{id}` continues to show original automated check statuses. Missing/failed checks need a successful rerun or the manual path described below.
5. **Submit.** The creator posts to `/revisions/{id}/submit` with `reviewer_id`, `expected_item_version`, `expected_run_id` and `expected_source_epoch`. Use `workflow_version` from a freshly loaded content record, the latest run ID and that run's source epoch. The server checks the current epoch independently. All required checks and blockers must be resolved; state becomes `in_review`.
6. **Decide.** The assigned separate reviewer posts to `/revisions/{id}/decisions` with the same three expected fields, `kind: "approved" | "changes_requested"`, and a meaningful rationale. Approval repeats every integrity check. A manager/admin role does not confer approval permission. Only one final decision is allowed per run. After changes are requested, create a new revision or analysis before resubmitting; old decisions remain in history.
7. **Export.** `GET /revisions/{id}/export` returns JSON containing the exact approved canonical text, SHA-256, context, immutable decision and a frozen evidence record. The record includes source versions, original/effective checks, model metadata, findings, resolutions, manual attestations and the comments present at approval. The frontend can save this JSON or offer a plain-text download from its `text`; the backend does not claim to recreate or approve an original PDF/image binary.

After a workflow mutation, reload content to obtain the incremented `workflow_version`. A 409 means the browser's version/run/source snapshot is stale, required checks/blockers remain, or the state transition is not permitted. Preserve creator edits when reloading. Do not make a silently repeated approval request with guessed updated values; the reviewer must see the changed record.

## Human completion of unavailable checks

This is an explicit human review path, not a generic “ignore failures” control. The assigned reviewer may post to `/runs/{id}/manual-checks` after the run reaches a terminal state, with category, `outcome: "complete" | "not_applicable"`, rationale, `expected_item_version` and source references. Completed checks require snapshot evidence; when category rules exist, at least one cited source must contain such a rule. Not-applicable is rejected if a source rule exists for that category. The current intake is canonical text; the reviewer must explain any scope exclusion rather than extrapolate whole-product accessibility/visual compliance.

Attestations are immutable and revision/run/reviewer-specific. Duplicate category attestations from that reviewer are rejected; a new analysis starts a new review. Generic finding exceptions do not satisfy missing checks. A source change/expiry still requires fresh analysis and cannot be waived with an attestation. If the assigned reviewer changes, earlier reviewers' attestations and exceptions do not satisfy the new review.

Exports preserve failed/unavailable automated statuses separately from the effective human-completed status, identify each human check, and include its rationale/source references. The automated run remains `incomplete` if that was its original outcome. Approval means the required review work was completed by automation and/or these disclosed human checks, not that the model or deterministic engine passed everything.

## Integrity behaviour

- Content-item locks serialise edits, assignment, resolution, submission, approval and export. Brand locks serialise decisions/exports with source activation. The lock order is item then brand; reviewer role is rechecked and held stable for final decisions. See [PostgreSQL row-locking documentation](https://www.postgresql.org/docs/current/explicit-locking.html).
- Expected workflow version, revision number, latest run ID and source epoch must match. Queued/running analysis cannot be approved. The server checks all six required categories; missing entries are incomplete.
- Only authorised resolution events clear blockers; the mutable finding display status alone is insufficient. Revoked reviewer privileges prevent further approval and fresh export.
- Decision, evidence snapshot, content state and audit event commit in one transaction. The tested rollback path leaves no partial approval.
- Export checks current revision/source eligibility and decision hash while holding locks, materialises its response, then commits the export audit event. A later source change cannot recall a previous download; it prevents subsequent exports.
- Source changes or expiry expose `approval_stale: true` on previously approved current content. The stored historical `approved` state/decision is retained; show a “Re-review required” badge when stale. `/review` also exposes a `stale` flag.
- Editing after approval creates a new draft. It inherits neither approval nor exceptions. Old revision review records remain readable to authorised collaborators, but fresh approved export is limited to the current eligible revision.
